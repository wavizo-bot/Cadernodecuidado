# CADERNO DE CUIDADO — MANUAL DO PROJETO
# Atualizado em 29/10/2026

## 1. O que é

Agenda digital de apoio ao acompanhamento de gestantes e crianças de 0 a 2 anos.
Funciona offline por padrão e está disponível como:

- app Windows (MSIX, WebView2 + host C#);
- app Android (Capacitor/Gradle, AAB para o Google Play);
- PWA/web (bundle single-file + service worker).

O app organiza cadastros, consultas, faltas, cancelamentos, expectativas, agenda
confirmada e pendências. Não é prontuário, sistema oficial, dispositivo médico,
protocolo de urgência ou substituto da decisão de um profissional habilitado.

## 3. Arquitetura

### App web

- `index.html` — bundle React single-file (~1,9 MB). É a fonte do app web.
- `sync-ui.js` / `sync-ui.css` — cliente de sincronização e modal do Google Drive.
- `terms-modal.js` / `terms-modal.css` — aceite bloqueante, termos v1.1 e links
  para os documentos públicos.
- `manifest.webmanifest`, `sw.js`, `icons/` — PWA e cache offline.
- Chaves de armazenamento local:
  - `caderno-cuidado-registros-v1` — fichas;
  - `caderno-cuidado-config-v1` — configurações da equipe;
  - `caderno-drive-sync-v1` — metadados de sincronização (deviceId, geração,
    lamport, heads, fingerprint etc.);
  - `caderno-sync-ops-v1` — operações por registro;
  - `caderno-sync-heads-v1` — cabeças materializadas;
  - `caderno-sync-conflicts-v1` — conflitos pendentes;
  - `caderno-termos-v1` — aceite dos termos (versão, data, instalação).

### Host Windows

- `MSIX/src/Launcher.cs` — WinForms + WebView2, compilado com `csc.exe`
  (.NET Framework 4.x, C# 5).
- `MSIX/Build-MSIX.ps1` — copia o app, carimba versão, compila, empacota e assina.
- O host expõe `chrome.webview.hostObjects.cadernoDrive` com:
  `GetState`, `CheckRemote`, `RestoreFile`, `Restore`, `Backup`, `Login`,
  `Logout`, `ResetCloud`, `GetAppVersion`, `Quit`.
- OAuth usa loopback local (nunca IP literal), PKCE,
  escopo `drive.appdata`, token em DPAPI.
- O host lista TODOS os arquivos válidos da pasta `appDataFolder`, sem filtro
  por tamanho, e usa o `modifiedTime` do servidor.

### Android

- `android/` — projeto Capacitor 7 + Gradle 8.13, AGP 8.13.2, compile/target 36,
  minSdk 24, R8 full mode.
- `android/package.json` — versionName; `android/version-code.txt` — versionCode.
- `android/scripts/stage-web.mjs` — copia a fonte web da raiz (incluindo
  `sw.js`), adiciona `android.css`/`android-bridge.js`, carimba a versão e troca
  “navegador” por “aparelho”.
- `android/android/app/src/main/java/caderno/decuidado/app/`:
  - `DrivePlugin.java` — contrato do plugin; sempre resolve `{ok:false,error}`;
  - `DriveApi.java` — Drive v3 `appDataFolder`, lista todos os arquivos,
    restaura por `fileId`, upload por dispositivo, reset;
  - `OAuthFlow.java` — sessão do login nativo do Play Services: guarda o
    access token do seletor nativo, confere o escopo `drive.appdata`,
    busca o e-mail e mantém a renovação silenciosa (refresh token de
    versões antigas). O consentimento é SEMPRE a janela nativa
    (`AuthorizationActivity`, seletor "Escolha uma conta"); NÃO existe
    Custom Tab, navegador do sistema, `LoginWindow` nem WebView de login
    (regra A8 e pedido do usuário);
  - `MainActivity.java` — repassa o resultado da `AuthorizationActivity`
    ao `DrivePlugin` via `onActivityResult` (o Bridge do Capacitor 7 só
    repassa requestCodes do mecanismo legado de plugin); entrada do app;
  - `AuthStore.java` — refresh/access token cifrado com Android Keystore;
  - `FilesPlugin.java`, `PrintPlugin.java`;
- `android/android/app/src/main/assets/google-client.json` é local e ignorado.

## 4. Modelo de sincronização (v2)

Cada dispositivo grava um arquivo próprio:
`caderno-ops-<deviceId>.json`. O arquivo legado `caderno-backup.json` continua
sendo lido para migração. O payload v2 tem:

```
{ v: 2, app: "caderno", generation, deviceId, ops: [...], state: {reg, cfg}, checksum }
```

Cada operação tem `opId` (UUID), `deviceId`, `docId`, `type` (`put`/`del`),
`baseVersion`, `baseOpId`, `version`, `data`, `createdAt` e, quando for
resolução, `resolves: [opIdLocal, opIdRemoto]`.

Regras:

- exclusões usam tombstones (`type: "del"`), nunca remoção silenciosa;
- `recompute()` reconstrói heads e conflitos a partir das operações;
- duas edições concorrentes preservam as duas versões e geram conflito;
- a resolução escolhe uma versão, grava `resolves` e é propagada;
- uma terceira ramificação continua em conflito e recebe nova cabeça;
- geração maior bloqueia poll/merge até decisão explícita do usuário;
- o checksum é calculado sobre o estado canônico; payload adulterado é rejeitado;
- não há escolha por relógio, tamanho de arquivo ou “mais recente” automático;
- o polling ocorre a cada 15 s quando a integração está ativa.

## 5. Regras de agenda

- A próxima data é o marco seguinte depois da última consulta realizada.
- Consulta realizada até ±4 dias da data ideal cumpre o marco anterior e o
  próximo marco parte da consulta realizada.
- Distância maior que 4 dias abre decisão humana: manter o mesversário ou
  iniciar um novo intervalo.
- Intervalos menores que 20 dias geram aviso.
- Falta e cancelamento NÃO consomem o marco ideal; a expectativa continua
  aguardando encaixe.
- Um dia, um evento: não pode existir mais de uma realizada, falta ou
  cancelamento no mesmo dia. O app bloqueia o conflito; ao salvar um evento,
  remove entradas agendadas conflitantes daquele dia.
- O resultado é apoio à decisão, não prescrição.


Copia o app da raiz para `docs/app/`, carimba a versão web e copia os seis

WebView2 em `MSIX/staging/` e o client OAuth Desktop local. O script carimba
